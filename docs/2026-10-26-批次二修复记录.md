# 批次二：设备台账识别与请求边界

基线 iOS `af844ec`；Android `ff5f8be`。版本保持 3.1.0（18），保留“看教程”。不修改 Android，不合并主分支。

## Android 依据及修改

- `data/MacFormat.kt`、`DeviceInfoCache.kt`：台账查询原地址优先，只有成功且 data 为空时才尝试清首字节最高两位的小写候选。错误、断网不继续尝试。扫描、上次使用、恢复订单使用同一查询实现。
- `MainViewModel.fetchInfo`：占用查询使用返回台账的 snCode，不再误用广播地址；内存缓存同时索引广播地址及业务 SN。
- iOS 特有连接映射：服务端确认台账后，将业务 SN/MAC 对应到实际扫描的 CBPeripheral UUID。不能用派生地址直接制造连接对象；别名冲突时拒绝连接，保持开关阀前状态帧身份核对。
- `BluetoothScanner`/附近列表的稳定点选思路：扫描期间原位更新，扫描结束再排序。修正原先注释说不实时排序、实现却每次重排的矛盾。厂商数据仍严格限制为 8 字节、公司 ID 为 0000。
- Android `NetworkModule`/`checkKickEx`：保留 HTTP 401/403 类型，不包装为普通 transport 错误。断网仍是网络故障，不踢下线。
- Android 会话作用域取消思路的第一层防护：登录建立/退出时更新请求代次；响应返回时检查代次与取消状态。GET、表单 POST、JSON POST 都拒绝旧会话响应。心跳另行检查代次，不能用旧响应更新余额或踢掉新账号。

## 明确边界

本批不等于完整会话任务隔离。旧结算循环可能捕获错误后继续下一轮，BLE/GATT 已发出的命令也不能由 HTTP 响应拦截撤回；全链路任务取消与恢复记录的账号归属仍需下一批专项处理。

不放宽设备状态帧 MAC 校验，不按信号最强选择设备。若学校设备状态帧自报地址与台账不一致，需要日志证据后单独分析，不能靠地址派生跳过校验。

## 检查与真机验收

- 新增离线测试：候选顺序、空台账回退、原地址命中零额外请求、业务失败不回退、广播解析、确认映射与冲突拒绝。
- 独立编译生产 ApiClient，用 URLProtocol 拦截全部网络，覆盖三种请求的 401/403、旧会话成功/失败响应、普通断网和已取消请求。不会发送真实请求。
- 真机：扫描中列表不跳位；现有学校设备名称正常；有派生 MAC 的学校能打开正确设备详情、连接目标设备；两台表相邻时不串控制。
- 下一批：完整会话任务生命周期与恢复订单账号归属；之后账单磁盘缓存、通知及 UI 剩余差异。
